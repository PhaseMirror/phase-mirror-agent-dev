The ``two legal persons'' and ``second cryptographic identity''
constraints have been separated into two distinct acts to prevent
dissonance between document acceptance and runtime unfreeze logic.

\hypertarget{document-accept-governance}{%
\subsubsection{1. Document Accept
(Governance)}\label{document-accept-governance}}

This phase operates the H2 lever for ADR acceptance (e.g., ADR 003).

\begin{itemize}
\tightlist
\item
  \textbf{Mechanism}: Two named persons, holding two distinct keys, each
  sign the SHA-256 hash of the canonical ADR bytes.
\item
  \textbf{Storage}: Signatures stay detached. Do not append signatures
  to the document body, as this would alter the signed bytes.
\item
  \textbf{State}: The document status remains \texttt{Proposed} until
  both signatures verify.
\item
  \textbf{Owner}: The two key holders.
\item
  \textbf{Metric}: \texttt{git\ verify} or an equivalent
  detached-signature check on that blob.
\end{itemize}

\hypertarget{runtime-unfreeze-engine-execution}{%
\subsubsection{2. Runtime Unfreeze (Engine
Execution)}\label{runtime-unfreeze-engine-execution}}

\textbf{DO NOT RUN.}

\begin{itemize}
\tightlist
\item
  \textbf{Constraint}: No P\_2/P\_3 keygen, no out-of-band handshake, no
  Sedona compile for a ProofHash, and no R3-FREEZE clear.
\item
  \textbf{Condition}: Execution is suspended until a public path names
  the verifier, the freeze flag, and the proof object. That path does
  not currently exist.
\item
  \textbf{Rationale}: A document-accept rule cannot be operated as a
  runtime unfreeze. Sedona Spine as a certify stage is already Unbound
  in the kiln register. A workflow file is not an engine that refuses
  execution until two signatures arrive.
\end{itemize}
